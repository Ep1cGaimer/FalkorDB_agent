## Scope

- **S1 — Configurable repository integration.** Accept a Git repository path and selected revisions without requiring the shop fixture layout, `release.json`, or `codec.py`. Use a shared repository/history model and language-specific extraction adapters. A new repository using supported languages must require configuration rather than edits to core queries or orchestration. Declare supported languages and extraction limits; universal language support is not required for v1.
- **S2 — Useful code and history evidence.** Index files, symbols, supported dependency relationships, commits, tags, and available release notes. Connect code to its revisions so investigations can trace dependencies, identify affected components, explain changes between releases, and investigate when fixes appeared or disappeared. Preserve repository, revision, path, source span, content hash, and extraction provenance; distinguish parsed facts from inferred relationships.
- **S3 — Correct revision handling.** Preserve Git ancestry, including branches and merges, and handle renamed or deleted files without mixing identities across revisions or repositories. Check evidence at the requested revision: an ancestor containing a fix does not establish that the fix remains after a revert or later modification. Report uncertainty when change identity or backport equivalence cannot be established.
- **S4 — Large histories with bounded retrieval.** Support FalkorDB queries across many releases and dependency hops through bounded results and pagination, with visible coverage and truncation. Support incremental indexing, reuse unchanged content, and invalidate affected evidence after updates. An interrupted import must be recoverable without presenting its partial index as complete. Initial indexing and updates must have measurable time and resource costs.
- **S5 — Accessible investigation.** Carry repository and revision selection through the CLI, API, and existing MCP bridge into the same investigation workflow. Return source-backed findings and explicit gaps, allowing code/history retrieval without project-specific runtime instrumentation.
- **S6 — Preserve verification boundaries.** Keep runtime compatibility checks optional and adapter-based where project-specific evidence and executable checks are available. Ingestion must not execute repository code. General retrieval must not inherit the fixture harness's execution assumptions or claim compatibility from source evidence alone. Production deployment and universal runtime verification are outside v1.

## Evidence

- **E1 — Integration and access (S1, S5).** Retain the existing fixture as a regression baseline, then demonstrate onboarding at least two independent real repositories, including one unseen during implementation, without core query or orchestration changes. Exercise repository/revision selection through the CLI, API, and MCP bridge. Report configuration effort and adapter limitations. One well-supported language is sufficient initially; cross-language generality requires additional evidence.
- **E2 — History correctness (S2, S3).** Use independently prepared, held-out questions with expected answers and revision-specific source locations. Cover dependencies, distant releases, branches/merges, reverts, renames/deletions, ambiguous requests, and missing evidence. Include a backport case if claiming backport support. Score retrieved evidence separately from final answers and check that citations resolve to the requested repository and revision.
- **E3 — Scale and updates (S4).** Include a real repository whose code/history exceeds a practical single-prompt context budget and has enough history to exercise pagination beyond the current fixture traversal. Declare corpus sizes and performance budgets before measurement rather than requiring arbitrary file or tag counts. Record indexing/update time, index size, peak memory, query latency, truncation, and failures. Demonstrate changed/deleted evidence invalidation and recovery from an interrupted import.
- **E4 — FalkorDB benefit (S2–S4).** Compare against direct plaintext context where it fits and a practical plaintext search/file-reading baseline at larger scales. Use the same raw source/history, model, settings, task instructions, and resource budgets; report context-limit failures. Measure grounded answer accuracy, evidence recall/precision, citation validity, wrong-revision answers, tokens, tool calls, latency, and costs. Set a meaningful improvement threshold before evaluation: better accuracy at a comparable budget or lower token/cost usage without reduced answer and evidence quality. Include indexing costs and repeated paired runs; report results per repository as well as overall.
- **E5 — Reproducibility and boundaries (S1–S6).** Preserve commands, repository/revision manifests, extraction coverage, configuration, model/prompt identifiers, raw retrieval traces, answers, usage, timings, and scoring decisions. Record all attempted runs and incomplete results. Verify that ingestion does not execute repository code and that unsupported runtime checks remain explicit gaps. Existing fixture results and the documented SQL tie do not establish large-codebase advantage.

## Status Rules

- Track S1–S6 against their corresponding evidence as `PROPOSED`, `IN_PROGRESS`, `VALIDATED`, or `BLOCKED`. All start as `PROPOSED`. `IN_PROGRESS` requires an implementation or experiment reference; `VALIDATED` requires reproducible E1–E5 evidence applicable to that requirement; `BLOCKED` requires a specific obstacle and next action.
- Report integration, history correctness, scale, and FalkorDB benefit separately. A working importer or passing fixture test cannot validate all four. Limit claims to the measured repositories, languages, revisions, sizes, and workloads; broader feasibility remains conditional until demonstrated.
- Claim substantial retrieval advantage only when the predefined E4 threshold passes against the stronger applicable plaintext baseline. Preserve ties, regressions, failed runs, and uncertainty. Changes to held-out questions, budgets, or thresholds after inspecting results require a new evaluation with the original results retained.
- Treat unsupported languages/relationships, incomplete imports, stale evidence, missing history, and truncated retrieval as explicit coverage gaps. Missing graph edges do not prove absence of dependencies. Cite only available evidence and request clarification when the repository, revision, or requested change is unresolved.
- Preserve runtime dispositions where runtime verification applies: an observed applicable incompatibility yields `BLOCKED`; otherwise missing required evidence yields `NEEDS_EVIDENCE`; `BOUNDED_PASS` requires current passing receipts for every modeled obligation. Retrieval-only findings do not receive a compatibility pass. Revalidate affected evidence and claims after source, extractor, query, model, or adapter changes.
