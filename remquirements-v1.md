## Scope

- **S1 — Configurable repository integration.** Accept a Git repository path and selected revisions without requiring the shop fixture layout, `release.json`, or `codec.py`. Use a shared repository/history model and language-specific extraction adapters. A new repository using supported languages must require configuration rather than edits to core queries or orchestration. Declare supported languages and extraction limits; universal language support is not required for v1.
- **S2 — Useful code and history evidence.** Index files, symbols, supported dependency relationships, commits, tags, and available release notes. Connect code to its revisions so investigations can trace dependencies, identify affected components, explain changes between releases, and investigate when fixes appeared or disappeared. Preserve repository, revision, path, source span, content hash, and extraction provenance; distinguish parsed facts from inferred relationships.
- **S3 — Correct revision handling.** Preserve Git ancestry, including branches and merges, and handle renamed or deleted files without mixing identities across revisions or repositories. Check evidence at the requested revision: an ancestor containing a fix does not establish that the fix remains after a revert or later modification. Report uncertainty when change identity or backport equivalence cannot be established.
- **S4 — Large histories with bounded retrieval.** Support FalkorDB queries across many releases and dependency hops through bounded results and pagination, with visible coverage and truncation. Support incremental indexing, reuse unchanged content, and invalidate affected evidence after updates. An interrupted import must be recoverable without presenting its partial index as complete. Initial indexing and updates must have measurable time and resource costs.
- **S5 — Accessible investigation.** Carry repository and revision selection through the CLI, API, and existing MCP bridge into the same investigation workflow. Return source-backed findings and explicit gaps, allowing code/history retrieval without project-specific runtime instrumentation.
- **S6 — Preserve verification boundaries.** Keep runtime compatibility checks optional and adapter-based where project-specific evidence and executable checks are available. Ingestion must not execute repository code. General retrieval must not inherit the fixture harness's execution assumptions or claim compatibility from source evidence alone. Production deployment and universal runtime verification are outside v1.

## Evidence

- **E1 — Integration and access (S1, S5).** Retain the existing fixture as a regression baseline, then demonstrate onboarding at least two independent real repositories, including one unseen during implementation, without core query or orchestration changes. Exercise repository/revision selection through the CLI, API, and MCP bridge. Report configuration effort and adapter limitations. One well-supported language is sufficient initially; cross-language generality requires additional evidence.
- **E2 — History correctness (S2, S3).** Use independently prepared, held-out questions with expected answers and revision-specific source locations. Cover dependencies, distant releases, branches/merges, reverts, renames/deletions, ambiguous requests, and missing evidence. Include a backport case if claiming backport support. Score retrieved evidence separately from final answers and check that citations resolve to the requested repository and revision.
- **E3 — Scale and updates (S4).** Include a real repository whose code/history exceeds a practical single-prompt context budget and has enough history to exercise pagination beyond the current fixture traversal. Declare corpus sizes and performance budgets before measurement rather than requiring arbitrary file or tag counts. Record indexing/update time, index size, peak memory, query latency, truncation, and failures. Demonstrate changed/deleted evidence invalidation and recovery from an interrupted import.
- **E4 — FalkorDB benefit (S2–S4).** Compare against direct plaintext context where it fits and a practical plaintext search/file-reading baseline at larger scales. Use the same raw source/history, model, settings, task instructions, and resource budgets; report context-limit failures. Measure grounded answer accuracy, evidence recall/precision, citation validity, wrong-revision answers, tokens, tool calls, latency, and costs. Set a meaningful improvement threshold before evaluation: better accuracy at a comparable budget or lower token/cost usage without reduced answer and evidence quality. Include indexing costs and repeated paired runs; report results per repository as well as overall.
- **E5 — Reproducibility and boundaries (S1–S6).** Preserve commands, repository/revision manifests, extraction coverage, configuration, model/prompt identifiers, raw retrieval traces, answers, usage, timings, and scoring decisions. Record all attempted runs and incomplete results. Verify that ingestion does not execute repository code and that unsupported runtime checks remain explicit gaps. Existing fixture results and the documented SQL tie do not establish large-codebase advantage.

## Status Rules

- Track S1–S6 against their corresponding evidence as `PROPOSED`, `IN_PROGRESS`, `VALIDATED`, or `BLOCKED`. All start as `PROPOSED`. `IN_PROGRESS` requires an implementation or experiment reference; `VALIDATED` requires reproducible E1–E5 evidence applicable to that requirement; `BLOCKED` requires a specific obstacle and next action.
- Report integration, history correctness, scale, and FalkorDB benefit separately. A working importer or passing fixture test cannot validate all four. Limit claims to the measured repositories, languages, revisions, sizes, and workloads; broader feasibility remains conditional until demonstrated.
- Claim substantial retrieval advantage only when the predefined E4 threshold passes against the stronger applicable plaintext baseline. Preserve ties, regressions, failed runs, and uncertainty. Changes to held-out questions, budgets, or thresholds after inspecting results require a new evaluation with the original results retained.
- Treat unsupported languages/relationships, incomplete imports, stale evidence, missing history, and truncated retrieval as explicit coverage gaps. Missing graph edges do not prove absence of dependencies. Cite only available evidence and request clarification when the repository, revision, or requested change is unresolved.
- Preserve runtime dispositions where runtime verification applies: an observed applicable incompatibility yields `BLOCKED`; otherwise missing required evidence yields `NEEDS_EVIDENCE`; `BOUNDED_PASS` requires current passing receipts for every modeled obligation. Retrieval-only findings do not receive a compatibility pass. Revalidate affected evidence and claims after source, extractor, query, model, or adapter changes.

## Rigorous Testing Goals and Acceptance Gates

These are required acceptance goals, not results. All T0–T11 start as `PROPOSED`; no new implementation, successful run, or hackathon outcome is asserted by this document. Passing these gates establishes a defensible submission within S1–S6; it cannot guarantee a judging result. Additional languages, relationship types, backport equivalence, or runtime adapters become claimable only after their applicable gates pass.

### T0 — Freeze the evaluation contract before testing

- Version an evaluation plan before opening held-out answers. Freeze the corpus and exact commit hashes, supported languages and relationship types, exclusions, task IDs and strata, independent oracles, scoring rubric, baseline implementations, model/version, prompts, decoding settings, resource limits, repeat count, and chosen T10 advantage gate. Separate development data from held-out data; the system must not read expected answers or scoring annotations during ingestion or investigation.
- Fill in explicit numerical budgets for cold indexing time, update time, index disk size, process/container peak memory, per-query rows/hops/tool calls/tokens, query timeout, p95 latency, demo duration, and monetary spend. State hardware, database version/configuration, tokenizer, context window, cache state, and concurrency. An unset budget prevents the corresponding gate from passing; choose budgets for the declared corpus and demo environment rather than inventing universal scale requirements.
- Use at least two independent real repositories, with at least one withheld from implementation and tuning. Pin immutable snapshots and make their source/history available to every comparison arm. At least one repository's declared source/history corpus must exceed the chosen model's usable single-prompt input budget; publish the token calculation, reserved output/tool budget, and included/excluded content. Synthetic repositories supplement real repositories for adversarial cases.
- **Pass/evidence:** a timestamped, hashed evaluation-plan manifest containing every field above and the independent reviewer's sign-off. Any post-result change creates a new evaluation version and preserves the earlier plan, attempts, and results. “Independent” means an author/reviewer who derives expectations from source and Git without using product answers; record authorship and any use of assistance.

### T1 — Configuration-only integration and fixture regression

- Onboard both real repositories from clean checkouts using documented configuration and declared adapters. Record elapsed setup effort, commands, configuration, extracted/excluded content, and difficulties. For the unseen repository, freeze the implementation first and retain before/after hashes of core query and orchestration code. A necessary core change invalidates that unseen trial; fix it and use a new unseen repository for the claim.
- Run ingestion from arbitrary repository paths, including spaces and Unicode, and select repositories with colliding file/symbol/tag names. Cover supported repositories without `release.json`, `codec.py`, or the shop directory layout. A deliberately unsupported language or malformed source file must produce an explicit coverage gap with path/reason and must not silently appear parsed.
- Preserve the independent fixture oracle: all eight cases must match exact dispositions, obligation sets, applicable probe outcomes, and gaps. Retain the SQL obligation-set control as a tie unless new measured evidence changes that result. Run the existing offline regression suite and applicable live FalkorDB/MCP integration tests; distinguish passes, skips, and failures.
- **Pass/evidence:** both real repositories onboard with configuration alone, all required regression cases pass, and repository-selection isolation tests have zero cross-repository evidence leakage. Publish configurations, code hashes, test reports, and limitations. One passing language validates only that language.

### T2 — Independently scored retrieval and answer quality

- Prepare at least 120 distinct held-out real-repository questions: at least 20 each for dependency/affected-component investigation, distant-release differences, branch/merge provenance, fix presence after later changes, rename/deletion identity, and ambiguity/missing evidence. Assign each question one primary stratum and include both repositories in every stratum. At least 40 questions must require two or more supported relationship hops or cross-revision reasoning. These complexity cases may overlap with the strata; repeated model runs do not count as new questions. Use development/pilot data to plan sample size for the chosen T10 effect and confidence bounds; 120 is a floor, not assurance of adequate statistical power.
- Include at least 30 negative or ambiguity cases within the suite, covering missing revisions/metadata, unsupported relationships/languages, ambiguous repository/tag/change names, and insufficient evidence. Add backport questions if claiming that capability. For each case, the oracle specifies required facts, acceptable alternative evidence sets, exact repository/commit/path/spans, expected uncertainty or clarification, and claims that would be incorrect. Do not score absence as proved when extraction coverage cannot establish it.
- Score retrieval before answer generation. Evidence recall is the fraction of required oracle facts supported by retrieved evidence; evidence precision is the fraction of retrieved evidence units that support the question or a necessary reasoning step. Freeze deduplication, evidence-unit definitions, and alternative-proof rules. A grounded answer passes only when all required conclusions are correct, material claims are supported, citations resolve, and required limitations/clarifications are present. An invented conclusion or wrong-revision citation fails the case.
- Average repeated-run scores within each question, then macro-average distinct questions for quality metrics; publish per-run results as well. Timeouts, errors, and unjustified abstentions on answerable questions receive zero answer score and zero evidence recall rather than disappearing from denominators. Empty retrieval on an answerable question receives zero precision. Predeclare genuinely inapplicable evidence metrics for clarification-only cases and report their separate counts. Critical zero-error gates apply to every run, not a majority vote.
- Run every question at least three times per arm with paired seeds where supported; otherwise record nondeterminism and randomize arm order. Blind answer scorers to the arm. Independently double-score at least 25% of cases, including every disputed, wrong-revision, or false-pass case; report initial agreement and retain both ratings and adjudications.
- **Pass/evidence:** overall grounded-answer pass rate ≥90%, each repository and each stratum ≥85%, macro evidence precision ≥95%, macro evidence recall ≥90%, and 100% valid citations for material answer claims. Wrong-repository/revision claims, fabricated citations, false definitive absence claims, and unsupported compatibility passes must be zero in the evaluated suite. Every negative/ambiguity case must expose the required gap or ask the necessary clarification without inventing the missing answer. Publish per-case scores, denominators, and uncertainty; a finite zero-error result is not a universal guarantee.

### T3 — Git history and identity correctness under adversarial changes

- Build an independently specified synthetic Git DAG covering linear history, divergent branches, merge commits, merge conflict resolution, a reverted fix, revert-of-revert, partial revert, later overwrite, cherry-pick/backport, reused symbol names, rename with edits, copy, deletion, and delete/recreate at the same path. Verify expected trees and ancestry with Git plumbing; do not use graph output as the oracle.
- Ask both “when was this introduced?” and “is it present at revision X?” before and after each change. Resolve tags to recorded commit hashes and test moved tags, detached revisions, missing/shallow history, and identical paths in separate repositories. Ambiguous rename/backport equivalence must remain uncertain unless supported by the declared adapter and evidence.
- Add at least 100 seeded generated histories with independently tracked expected file/change state. Test invariants: indexing order does not change results; adding an unrelated branch/repository cannot alter answers for a pinned revision; reverting a change changes current-presence conclusions; deleting a file preserves its earlier historical evidence. Save seeds and minimize any failing history into a regression case.
- **Pass/evidence:** 100% agreement with the deterministic history oracle and invariant tests; zero ancestry-only claims that a reverted or overwritten fix is still present. Publish Git-generation commands, expected trees/state, queries, returned evidence, and ambiguity cases. Real-repository held-out results must also satisfy T2.

### T4 — Index integrity, incremental updates, and interruption recovery

- Compare a clean full index with incrementally indexed results after add/edit/rename/delete, a branch merge, a moved tag, and extractor/schema changes. Assert equivalent normalized entities, relationships, provenance, coverage, and answers for the same manifest, excluding declared operational timestamps/IDs. Demonstrate that unchanged content is reused and affected cached evidence/claims are invalidated; reuse must preserve revision-specific identities.
- Inject deterministic failures during discovery, parsing, each persistence/checkpoint boundary, and final publication; also interrupt at seeded random points. Repeat imports, retries, and resume after a process restart. Test database unavailability and a failed update while a previously complete snapshot exists. Incomplete work must be visible as incomplete; any served previous snapshot must be explicitly identified by its manifest and revision.
- Test concurrent update/query behavior if supported. Otherwise, prove that conflicting operations are rejected explicitly. Queries must never combine old and new index generations or report a partial generation as complete.
- **Pass/evidence:** every injected failure is recoverable by the documented retry/resume/rebuild path without manual graph repair; resumed and clean indexes agree; retries create no duplicate logical facts; stale/deleted evidence cannot support current-revision answers. Record fault points, generation IDs, completeness markers, content-reuse counters, normalized comparisons, and recovery time.

### T5 — Bounded traversal and pagination without silent omission

- Exercise row counts of 0, 1, cap−1, cap, cap+1, and multiple pages; do the same at hop/depth boundaries. Include cycles, high fan-out, long histories, repeated names, empty pages, invalid/expired cursors, and evidence found only on the final page. Compare the union of pages to an independent full enumeration on controlled graphs.
- Require deterministic ordering, no duplicate/missing logical results, repository/revision-bound cursors, and explicit continuation/truncation/coverage metadata. Updates between pages must either preserve a pinned index generation or reject the cursor and require restart. Exhausting a row/hop/token/time budget must yield a visible partial result and withhold conclusions requiring omitted evidence.
- **Pass/evidence:** exact enumeration agreement in all controlled tests, all configured resource bounds respected, and zero “complete” or “no dependency/fix exists” answers produced from truncated required evidence. Publish boundary cases, cursors, page traces, row/hop counts, and the final coverage decision.

### T6 — Measured scale, performance, and operational cost

- Benchmark the real corpus exceeding one prompt and at least two smaller declared history/size slices. Count commits, tags, tracked/indexed/excluded files, symbols, relationships, bytes, and tokens. Include dependency depth and fan-out distributions so graph size cannot substitute for workload difficulty.
- Perform at least three independent cold full imports and three incremental-update trials per slice. Define cold state explicitly and separately measure warm runs. For query performance, use at least 100 measured requests per slice spanning all T2 strata, after a declared warmup, and run both single-request and a predeclared demo-concurrency workload. Record all attempts, timeouts, failures, p50/p95 latency, indexing/update time, disk size, peak process/container memory, token/tool usage, and actual model/database costs. Include failed requests in latency samples at their measured termination time and identify timeouts as censored at the deadline; report successful-request latency separately.
- **Pass/evidence:** every import/update completes within its frozen T0 time/memory/disk budget; each measured query workload meets its frozen p95 and hard resource limits with ≥99% successful requests, where success requires an on-time, structurally valid response rather than a swallowed error. Fault-injection requests are reported separately. T2 quality and T5 completeness gates must also hold at scale; fast incomplete answers do not count as successful investigation. Publish raw samples and hardware/configuration, and limit scale claims to measured sizes and concurrency.

### T7 — Consistent CLI, API, and MCP investigations

- Run the same repository/revision/question cases through all three surfaces against the same pinned index. Include a successful cited investigation, branch/release selection, ambiguity/clarification, unsupported content, missing repository/revision, incomplete index, truncation, and upstream model/database failure. Compare normalized semantic findings, citations, selected identities, gaps, and coverage; ignore only predeclared transport-specific fields.
- Test malformed/oversized inputs, timeout/cancellation, retries, MCP transport restart, and parallel requests selecting different repositories/revisions. Verify that selection survives follow-up questions and cannot silently fall back to the fixture or the most recently used repository. Errors must identify the failed operation and preserve honest status without exposing secrets.
- **Pass/evidence:** 100% agreement on deterministic identity/status/coverage contracts and oracle expectations across surfaces; live generated answers on each surface satisfy the same grounding rules. No request-state leakage or silent fallback. Retain CLI output, API requests/responses, and real MCP transport transcripts; mocked tool calls alone do not establish MCP integration.

### T8 — Safe ingestion and explicit verification boundaries

- Ingest test repositories containing executable import hooks, install/build scripts, Git hooks, malicious filenames/symlinks, and instructions embedded in code/release notes telling the agent to execute commands, switch revisions, or invent a pass. Use observable canaries and filesystem/process/network auditing to verify that ingestion does not execute repository code and repository content cannot authorize tool execution or alter system instructions. Contain path traversal/symlink escapes and avoid fetching arbitrary external content as an implicit ingestion side effect.
- Test evidence-only investigations with absent runtime adapters and with missing, stale, conflicting, truncated, or unsupported runtime evidence. Source retrieval alone must never emit `BOUNDED_PASS`. Keep runtime adapter execution an explicit separate workflow; any non-fixture execution capability needs its declared isolation model and corresponding tests before it is claimed.
- Where runtime verification applies, enumerate every modeled obligation independently. Inject applicable failure receipts, missing receipts, mismatched plan/source/snapshot/reader/route/record/environment identities, and changes after verification. Verify precedence: applicable failure → `BLOCKED`; otherwise any required gap → `NEEDS_EVIDENCE`; only complete current passing receipts → `BOUNDED_PASS`. Approval and simulation must reject stale/ineligible evidence, and repeated approved local simulation must remain idempotent.
- **Pass/evidence:** zero repository-code executions during ingestion, unauthorized effects, or false compatibility passes in these tests; 100% correct deterministic disposition/receipt checks. Preserve audit traces, canary results, adversarial inputs, and existing approval/simulation regression reports. State the tested threat model and fixture-only execution limitation.

### T9 — Prove FalkorDB supplies the tested evidence

- Trace held-out investigations from a real FalkorDB query through returned entities/paths and source citations to the answer. Capture parameterized query identifiers/parameters, repository/revision/index generation, row counts, pagination, timing, and extracted-versus-inferred provenance. Mocked queries, cached prerecorded answers, and rendered graph pictures do not satisfy this gate.
- Perform controlled graph ablations on a disposable index: remove a required dependency/history edge, make an evidence record stale, and interrupt retrieval. The affected question must expose a gap, follow an auditable alternative evidence path, or lose the supported conclusion. It must not retain an unsupported answer from hidden expected data or stale cache. A disabled graph service must produce a visible failure or explicitly labeled fallback whose results are excluded from graph-arm measurements.
- **Pass/evidence:** all selected ablations behave as specified and at least one reproducible multi-hop code/history investigation on each real repository shows graph retrieval contributing required evidence. Publish query-to-answer traces and ablation results. This gate establishes real use and causal contribution; comparative advantage still requires T10.

### T10 — Win the fair comparison before claiming an advantage

- Compare the graph arm with direct plaintext context wherever the same raw corpus fits and with a practical plaintext search/file-reading/Git-history baseline at every size. The search baseline must support iterative search, source spans, revision checkout/show, and follow-up reads; give it comparable development effort. Preserve the SQL control on the fixture. A context-overflow result excludes direct context as an applicable winner at that size but never excuses comparison with search.
- Give all arms the same raw evidence, model/version, answer instructions, decoding settings, output budget, tool permissions, and maximum token/tool/time budgets; retrieval-specific interfaces may differ and must be disclosed. Freeze prompts and tuning on development data. Include retrieval/tool-output tokens and failed attempts in usage, and disclose caching and retries. Randomize execution order and use the paired T2 repeats. Do not stop after a favorable run or discard a failed pair.
- Before running, choose exactly one primary gate against the stronger applicable plaintext baseline: **(A)** at least a 10-percentage-point gain in grounded-answer pass rate with mean input-token use and mean query cost each no more than 5% higher; or **(B)** at least 20% lower mean total input-token use with no decrease in grounded-answer pass rate or evidence precision/recall. Output tokens, latency, and total costs must be reported for either gate. An input-token reduction alone cannot be described as a monetary saving.
- Report paired effect estimates and 95% confidence intervals using at least 10,000 bootstrap resamples of distinct questions, stratified by repository/task stratum and keeping paired arms and repeated runs together. Repeats are not independent questions. For A, require the accuracy-gain point estimate ≥10 points and its interval lower bound >0. For B, require the graph/plaintext token-ratio interval upper bound ≤0.80 and quality-difference interval lower bounds ≥0 for answer pass rate, evidence precision, and recall. If the suite cannot resolve these bounds, report the result as inconclusive; do not lower the gate after inspection.
- **Pass/evidence:** the chosen gate passes against each applicable plaintext comparator, T2's absolute quality/safety gates pass, and no repository shows a lower answer pass rate or evidence recall than its stronger comparator. Publish per-repository/stratum results and regressions, not just aggregates; conclusions concern only these fixed repositories and workloads. Report initial and incremental indexing costs separately and calculate query-volume break-even using measured savings; when savings are absent, report no measured break-even. Failure or a tie leaves the advantage claim unvalidated even if the product works.

### T11 — Reproducible judge-facing evidence and demo readiness

- Produce one versioned evidence bundle containing the frozen plan, source/revision manifests, extractor/configuration hashes, implementation commit and dirty diff if any, environment/dependency versions, commands, raw retrieval/transport traces, model/prompt identifiers, answers/citations, usage/cost/timing samples, test reports, scoring rubrics, adjudications, confidence-interval code/seeds, and every attempted run. Link each S/E/T entry to exact artifacts and distinguish real measurements, synthetic cases, mocks, and replays. Redact credentials and unrelated personal data without removing scoring-relevant evidence.
- Have an independent reviewer reproduce deterministic tests from a clean environment and recompute reported scores/intervals from the bundle without unpublished local files or undisclosed scoring inputs. Also rerun a stratified live subset of at least 12 held-out questions across both real repositories and all six strata. Record fresh results and expected model variation; material grounding/status contradictions reopen the affected gate. State API/account/hardware prerequisites and any non-redistributable corpus restrictions.
- Rehearse a documented live demo three consecutive times from a reset state. Show configuration-based onboarding or its reproducible import receipt, a revision-specific multi-hop finding with navigable source citations, a revert/branch trap, a bounded/truncated or missing-evidence outcome, the comparison scorecard, and the specialized fixture failure/pass boundary. Include at least one fresh investigation on a real repository each time. Record duration and failures; label a replay as a replay and exclude it from live success counts.
- **Pass/evidence:** clean reproduction and score recomputation succeed, all three demos complete within the frozen demo-duration/resource budget, and every displayed quantitative claim links to evidence. A demo cannot override a failed acceptance gate. Retain a concise claim card with measured scope, baselines, effect/uncertainty, limitations, and the exact evidence-bundle version. Record current official submission requirements separately and verify required deliverables before submitting; these engineering gates do not replace the event's rules.

## Requirement-to-Test Traceability

All listed gates are required for the corresponding row. “Applicable” runtime/backport tests must be explicitly enabled or marked outside the claim boundary with a reason; they cannot be silently skipped. An implementation test, held-out evaluation, and evidence-bundle reproduction establish different things and are not interchangeable.

## Evidence Ledger and Claim Release Rules

- Maintain a machine-readable ledger with `requirement_id`, `test_goal_id`, `status`, `owner`, `implementation_ref`, `evaluation_plan_hash`, `corpus_manifest_hash`, `run_ids`, `artifact_links`, `observed_metrics`, `thresholds`, `failed_or_skipped_cases`, `limitations`, `reviewer`, and `validated_at`. `BLOCKED` also records the obstacle and next action. Initially every S/E/T entry is `PROPOSED`; this document supplies no implementation or validation references.
- A test goal becomes `VALIDATED` only when every mandatory clause and numerical gate passes on the recorded implementation/corpus. A required skipped test, missing artifact, incomplete run, or inconclusive statistical result prevents validation. Runs may have `PASS`/`FAIL`/`ERROR`/`SKIPPED` outcomes; requirement status continues to use only the four defined values. A failed test does not itself mean the requirement is `BLOCKED`: ongoing corrective work remains `IN_PROGRESS` unless a specific obstacle prevents progress.
- Validate each S1–S6 item only after all gates in its traceability row pass. Validate E1–E5 against their applicable rows and preserve separate conclusions for integration, history correctness, scale, verification boundaries, and advantage. Claim “v1 scope validated” only when S1–S6 and their evidence gates pass; claim “substantial FalkorDB retrieval advantage” only when E4/T10 also pass. Partial completion must name exactly which requirements are validated and which remain proposed, in progress, or blocked.
- An affected source/corpus/extractor/schema/query/prompt/model/adapter change moves the current affected validation back to `IN_PROGRESS` until the relevant tests rerun. Preserve historical validation and its hashes. If a holdout has informed a fix or tuning decision, treat it as development data for the next confirmatory claim and use fresh independently prepared held-out cases; keep the original failure visible.
- The final submission scorecard must show absolute counts and denominators, per-repository/stratum results, repeated-run variation and confidence intervals, all baseline ties/regressions, resource/cost measurements, unresolved gaps, and reproducibility links. “Production safe,” “all languages,” “all histories,” and “guaranteed winner” exceed v1 evidence and must not be claimed.
